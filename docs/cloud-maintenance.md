# 云端维护范围

## 结论

不需要维护数据库、账号系统、下载代理或常驻业务服务器。云端可以只是一组可缓存的 HTTPS 静态文件；大文件全部交给第三方托管。

推荐组合：

- GitHub仓库：源代码、清单、Schema和构建流程。
- GitHub Pages：发布签名后的 `channels/stable.json/.sig` 与 `channels/beta.json/.sig`。
- GitHub Releases：Root模块、自有后台程序、项目包和必要的自建rootfs产物。
- 官方上游Release/API：maa-cli、MaaCore和可直接使用的官方产物。
- 可选对象存储/CDN：只作为镜像，不成为唯一下载源。

## 我们必须维护的内容

| 内容 | 作用 | 是否包含大文件 |
| --- | --- | --- |
| `stable.json` / `beta.json` | 指定每个组件的版本、兼容关系和下载源 | 否 |
| 清单签名 | 防止清单或下载地址被替换 | 否 |
| SHA-256与文件大小 | 验证第三方托管文件完整性 | 否 |
| 兼容矩阵 | 声明Android、架构和Root管理器支持范围 | 否 |
| 更新说明 | 告知用户变化、风险和是否需要重启 | 否 |
| 紧急公告/阻断规则 | 阻止已知损坏版本继续安装 | 否 |
| 自有组件源码与构建流程 | 可重复生成模块、后台程序和项目包 | 否 |
| 发布验收结果 | 证明候选版本通过了哪些设备和回滚测试 | 否 |

私钥、Token和发布凭证不能写入仓库或清单。清单签名私钥只能放在受保护的发布环境；Root模块内只内置公钥。

清单源先与代码放在当前仓库的 `maa-phone-manager/manifest/channels/`，不单独新建仓库。只有当清单需要独立发布权限、独立维护团队或与代码完全不同的发布周期时再拆仓；客户端仍使用同一Schema和签名协议，无需跟着迁移实现。

## 第三方维护的内容

第三方负责文件传输和存储：

- GitHub Releases托管我们构建的模块、后台程序和项目包。
- Debian官方镜像托管Debian软件包。
- MAA官方发布源托管maa-cli、MaaCore和资源。
- 可选镜像/CDN托管上述文件的副本。

“第三方托管”不等于“第三方替我们决定版本”。我们仍需要选定具体版本、记录来源、固定哈希并验证兼容性。

## 不允许的清单写法

- 不使用会漂移的 `releases/latest/download/...` 作为唯一地址。
- 不下载后直接执行远端shell脚本。
- 不只校验文件名或HTTP状态码。
- 不在多个镜像之间接受不同哈希的同名文件。
- 不因主下载源失败就跳过签名或哈希检查。
- 不允许WebUI传入清单之外的任意URL。

## 下载源规则

每个产物记录一个主地址和零到多个镜像地址，所有地址必须对应同一个SHA-256。后台按顺序尝试：

1. 检查当前缓存是否已有相同哈希。
2. 尝试主地址。
3. 主地址网络失败后尝试镜像。
4. 任一来源下载完成后统一验证大小和SHA-256。
5. 校验失败时删除候选文件，并将该来源标记为本轮不可用。

## rootfs的特殊说明

如果没有可信上游直接发布适合本项目的Debian chroot tar包，可以由GitHub Actions从固定Debian官方仓库快照构建rootfs，再把产物上传到GitHub Releases。这样仍然不需要自建文件服务器，但我们必须维护构建配方、软件包锁定信息、SHA-256和许可证说明。

## 发布最小流程

1. CI构建自有组件并生成SHA-256。
2. 候选版本在明确支持的设备组合上执行安装、更新和回滚验收。
3. 产物上传第三方Release。
4. 生成引用不可变版本URL的候选清单。
5. 验证所有URL、大小和SHA-256。
6. 使用离线私钥或受保护CI环境签名清单。
7. 先发布测试通道，稳定观察后再更新稳定通道指针。

第三方服务临时不可用只影响新安装或检查更新，不能影响设备继续运行已安装版本。
